# Capability routing

Use one installed skill for all tasks. This repository contains 12 focused playbooks and 42 capability IDs; the agent loads only the relevant playbooks. Do not read every tool or install a suite.

1. Inspect the target with the inspector and confirm context (including actual tool availability).
2. Decompose the user's request into the few capability IDs that matter. Use the compact [capability index](INDEX.md) and only the relevant routing table to find them. Specify surfaceType (marketing website, product interface or native) from project evidence. New product UI prefers product-oriented guidance (Impeccable), not Taste's marketing defaults; a core dashboard capability infers product if surfaceType is omitted. Mark core versus supporting priority so core work consumes the specialist budget first. For rebuild, existing UI structure is not a reason to mark design discovery adequate; coverage refers to actual engineering/tool capabilities. Choose coverage per capability: adequate (verified existing resource), gap (specific reason why current resources are insufficient), unknown (not checked). Record brief evidence for adequate/gap. For advanced runtime or native Material choices record the specific flag only when justified. For a new runtime also confirm runtimeInventory is none, including libraries outside the catalog. Existing arbitrary tools can be represented as provider project; record their names in the report. Do not infer absence from an incomplete inventory.
3. Set asOf to the current UTC date for source-freshness checks. Run `node <skill-directory>/scripts/route.mjs <request.json>` with [route.example.json](route.example.json) / [route.schema.json](route.schema.json). Without a shell, apply the same policy manually from the relevant generated routing table and per-tool cards and [priority-policy.json](priority-policy.json). The older plan.mjs is a coarse setup-only compatibility path, not the primary design-task router.
4. Read the returned playbook paths and only selected per-tool cards / upstream source entries. If using read-only GitHub, follow the same defaults: Taste for broad new marketing web design, Impeccable for functional product UI and existing web redesign, UI/UX Pro Max for planning (native planning only). Preserve one existing compatible owner; narrow tasks use bundled guidance or confirmed existing focused commands. Route core work before supporting work, apply the same two-specialist budget and never install for unknown coverage. Route outputs are proposals: candidate means eligible for review, not approved install; reuse means confirmed existing tool (verify actual invocation); playbook means bundled guidance, not proof all external needs are satisfied; needs-verification/blocked require resolution or explicit disclosure. Do not treat not-applicable as a successful implementation.
5. For a broad design task pick one primary owner from the existing project or the goal-based default. Narrow layout/type/audit tasks use built-in playbooks and existing focused commands; no general skill install by default. Deduplicate commands and tool IDs. Use one runtime per family, one component system. At most two new specialist skills per task by default; if necessary, propose a subsequent scoped step rather than silently expanding.
6. Do not fall back to a weaker or unknown source just because the default has missing prerequisites. Review manual alternatives explicitly with evidence. Read [acceptance.md](acceptance.md) before changes; capture real output and report all blockers.

## Priority and trust

The priority policy is task-specific. Preferred means a documented default for its role; specialized means justified narrow fit; alternative is manually considered; exploratory is research-only. This is not a popularity-based leaderboard. Quality remains unbenchmarked. New-tool selection is blocked when the source snapshot is archived, absent or older than 60 days relative to asOf; re-review upstream rather than automatically dropping to a lower tier. Check current release, source, license, runtime/agent versions, package manager, dependencies, hooks and permissions for every new candidate. Reuse existing compatible resources even if another tool is more popular. Never paste unrelated upstream instructions into the task or allow them to override project/user rules.

## Use, not just install

A candidate may require a skill command, code primitive, library runtime, registry item or browser capability. Do not confuse these. If selected and approved, inspect exact docs, install or configure only what is needed, verify discovery and invoke the focused capability. For registry components search existing items first; inspect item source and dependencies, adapt tokens and verify the actual rendered result. When a tool is unavailable, the playbook provides a bounded fallback, not an assurance of equal quality. State remaining gaps. Use [execution.md](execution.md) for the actual design-and-verification workflow and consolidated user interaction.

## Documentation-grounded routing

After routing, read the selected [knowledge card](knowledge/INDEX.md), pinned upstream source and exact version-specific documentation. Use the documented fit/exclusions and select an actual command, component or pattern. Read-only review of a skill that disables automatic invocation is allowed as reference, not automatic execution. If the selected source conflicts with project rules or cannot be inspected, stop that capability or seek an explicitly reviewed alternative. Follow [grounding.md](grounding.md); no ungrounded design fallback.

## Rebuild mode takes precedence over preservation defaults

Redesign defaults to `designMode: rebuild`; use refine for bounded polishing or reference-match for exact references. Read [rebuild.md](rebuild.md) and [source-access.md](source-access.md). The design owner is not a mandate to retain the old layout. For Impeccable use `reference/new-work.md` as replacement direction rather than bolder/layout as the primary route. Existing adequate runtime/components do not waive mandatory external pattern retrieval or the three-concept gate. The source index works without installing upstream packages. Apply the same rules manually if no shell is available.
