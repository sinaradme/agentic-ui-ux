# Rebuild mode — non-negotiable for structural redesign

Default for a redesign request: rebuild. If the user specifically asks for polish, small fixes or preservation, use refine. If they request matching an exact reference, use reference-match. Explicit directions such as from scratch, rethink the structure, creative redesign, discard old layout, new grids/carousels, or redesign each section require rebuild. Do not silently downgrade to refine. "Keep functionality" does not mean "keep composition."

## 1. Separate constraints from inertia
Capture the current rendered page and list every in-scope section. Preserve content truth, routes, data, business rules, accessibility, security, explicit brand/user constraints, and user-accepted exclusions. The old layout, cards, grid, navigation pattern, motion and styling are baseline evidence, NOT design requirements. Existing components/runtimes may be reused as engineering primitives without inheriting their old composition. If the user relaxes an old visual system, record the scope and replace it; do not change unrelated areas. For a functional product keep safe task behavior, density, discoverability, and platform conventions; novelty must improve the experience.

## 2. Mandatory external discovery, even when existing dependencies work
Do not use only project files or the bundled short playbooks. Read [source access](source-access.md) and [pattern index](patterns.md). Use the actual upstream new-work path for Impeccable instead of bolder/quieter/layout as the main direction. For each in-scope section inspect at least two concrete, meaningfully different source-backed patterns (at least one official external source per section). Retrieve actual text, component source, example or approved visual reference; never merely cite a homepage. Use source.mjs or agent's GitHub/browser/file tools. Record exact locator, version, observation, how it differs from baseline, and reuse the receipt across sections only when applicable. Read-only research needs no dependency installation; it cannot be skipped because the project already uses a component library. If source access is blocked, report and resolve it; no cosmetic fallback labeled rebuild.

## 3. Concept tournament
For EVERY section, construct three distinct candidate structural directions from the inspected patterns: content organization, layout topology, focal hierarchy, interaction/navigation model, and motion grammar. Candidate names alone do not count. Use small sketches (actual HTML wireframes, local screenshot comps or other reviewable schematics) before editing production UI. At least two candidates must change two of topology, content hierarchy and interaction model relative to baseline. All three must be structurally different from each other (not palette/spacing changes). Compare suitability, accessibility, responsive behavior and implementation cost. Pick the strongest task-fit option, not the least invasive one. If the user delegated creative decisions, select internally and continue; do not ask them to pick every section. Retain one coherent page-level thesis, avoid repetitive patterns and avoid novelty for its own sake. If a section has fixed/regulated structure, explicitly record the user-approved exception; otherwise do not silently preserve it.

## 4. Build and independently inspect
Implement selected compositions on an isolated branch or local preview where authorized. Change structure, not merely styles. Reuse an existing carousel runtime only as the engine for a genuinely different interaction/composition; replace it if the reviewed gap requires another and installation is authorized. Use meaningful motion with interruption, reduced motion, touch/keyboard and fallback. Test every section as implemented at relevant desktop/mobile or native sizes. Inspect before and after visually, compare actual structural axes with the selected candidate, and record screenshots/interaction evidence. If actual result collapses to old topology, hierarchy and interaction, reject and rework. Do not claim novelty or quality solely from a passing build. 

## 5. Gate
Use [rebuild.example.json](rebuild.example.json) and `node <skill-directory>/scripts/check-rebuild.mjs <record.json>`. The same rebuild data is required in the grounding preflight/final record when route.designMode is rebuild; use `check-grounding.mjs` as the overall gate. Record exact approved scope, source receipts, baseline, three candidates, selected concept, and final observed axes/evidence. Any missing scoped section, unresolved source, insufficient structural change, or missing visual/interaction evidence blocks completion. On read-only agents apply the same checklist manually. Structural validation cannot prove an agent's claims or aesthetic merit; compare actual rendered artifacts. Only explicit user-approved exceptions can preserve a section. Do not ask for permission to perform routine creative choices already authorized.

The machine-readable record uses controlled structural axes (topology, hierarchy, interaction, motion), separate source receipt IDs and before/after artifacts. Two structural axes must change for the selected concept and at least one other candidate; changing motion alone never qualifies. All three sketches must be distinct and at least two different external pattern families must be inspected. Base/Radix variants of the same carousel count as one family. Official documentation scope URLs are accepted only for concrete item/API pages. A source receipt records actual inspection, not proof of installation. See the example for exact fields. Final review must independently classify actual rendered structure, not simply copy candidate labels.
