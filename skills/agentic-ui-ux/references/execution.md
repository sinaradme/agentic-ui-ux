# Execution workflow

The user gives a design task, not a list of libraries. The agent owns the investigation and selection, within the user's authorization.

## 1. Understand and route

Read the brief, target rules and actual project. Infer what is clear; ask only for a material missing requirement (for example target platform, brand constraints, permission). Capture a baseline for existing screens. Identify core tasks and supporting tasks, and concrete acceptance criteria. Use the compact capability index, relevant routing tables and project evidence. Do not ask the user to choose between equivalent libraries.

## 2. One concise decision

Show the design direction, project assets/components/runtime to reuse, the minimal new tools if any, why each is necessary, and one concrete implementation/verification plan. Use bundled playbooks if they are adequate. A genuine advanced gap must remain open if no suitable tool can be used. Do not claim equal quality from an unverified fallback.

If changes need approval, present a consolidated list of exact reviewed package/skill versions, commands, working directories, configuration changes, licenses, permissions, hooks and rollback. Keep global/hook approvals separate. If the task is already authorized and no new permissions/installs are needed, proceed within scope; do not make the user reconfirm every routine design decision. Never invent authorization.

## 3. Implement with a single design owner

Use existing tokens, components, typography and visual language. Choose one visual thesis and make a representative screen or section before scaling across the product. For an explicit reference-match task identify the reference's measurable layout, spacing, hierarchy, motion and states; preserve functional behavior and use only permitted assets. Read only the chosen upstream skill command or reference. For components, locate an exact suitable item, review its code, dependencies and accessibility, then adapt it. For motion distinguish guidance from runtime; verify actual interaction, not just a still image.

## 4. Verify before completion

Use a real browser or native device and capture before/after when possible. Check primary user task, meaningful states, layout, responsive behavior, accessibility, reduced motion and relevant performance. Compare actual screenshots to the brief/references, not just a code diff. Fix highest-priority failures first and repeat up to three rounds by default. If the environment lacks tools, report blocked checks and request the smallest missing evidence. Never call a static screenshot a motion test or browser emulation a native device test.

## 5. Finish

Give a short outcome, verified checks, before/after evidence links where available, new dependencies and remaining gaps. Store reusable design decisions in the target project's existing design documentation only if authorized. Do not store sensitive project data in this public guide. Follow the [acceptance contract](acceptance.md).
